MediView

How the 45-day MVP works
4 services 15 tables 8 pages billing cut Azure deferred

One Study, one status, one source of truth. A patient self-registers and books inside a doctor's schedule; an admin simulates the x-ray import; a doctor reads the study in a single-writer locked viewport and finalizes a report with medications — the study closes or goes back for another read. The e-commerce billing sub-domain is out; the DDD core is in.

Patient

Self-registers
  • Books within a doctor's working hours
  • Sees live study_status, findings & medications
  • Reads their own study timeline — enforced from the JWT, not the URL

Doctor

Created by an admin
  • Worklist of studies booked in their hours (stat-first)
  • Diagnoses in the Cornerstone viewport under a Redis lock
  • Writes report + medications, finalizes, sets status

Admin

Seeded in the database
  • Onboards doctors (attests credentials — no upload flow in MVP)
  • Simulates the .dcm x-ray import into a Study
  • Break-glass override & force-release — always audited

Study status lifecycle — the single source of truth

Import never changes the status. A study stays todo until a doctor opens it under lock.

booked, not read doctor holds the lock another read requested finalized, immutable
The single-writer lock is the star. Redis holds the authoritative lock (SET NX PX + owner token, Lua compare-and-delete); Postgres study_locks mirrors it for the UI and the audit trail. Everyone else sees the study LOCKED. If the two disagree, Redis wins.
