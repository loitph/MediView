MediView — Solution Architecture

DDD · Clean Architecture · Microservices · the 45-day MVP

Four .NET 10 services behind a thin YARP gateway, each owning its own PostgreSQL schema. Every service is four Clean-Architecture layers over a shared building-blocks kernel; the Study aggregate carries the workflow's single source of truth, and services coordinate by choreography — reacting to integration events, never calling each other on the write path.

01

Container topology

One Blazor origin talks to one gateway. The gateway fans out to four independently deployable services. Redis, RabbitMQ, Postgres and Seq are shared infrastructure — the services are not.

02

Clean Architecture — the four layers every service repeats

Each of the four services is the same four projects. Dependencies point inward only: the Domain knows nothing about EF, HTTP or Redis. No MediatR — a ~40-line hand-rolled dispatcher with Result<T> and FluentValidation pipeline behaviours does the job.

Api outer

Minimal-API endpoints, JWT policies, error-handling middleware, DI composition root. Translates HTTP ⇄ commands/queries.

↓ depends on

Infrastructure adapters

EF Core DbContext (snake_case, xmin concurrency), repository implementations, Redis lock adapter, IBlobStore disk adapter, MassTransit, typed HttpClients.

↓ depends on

Application use cases

Command/query handlers, validators, port interfaces (IStudyLockService, IIdentityApi), DTOs. Orchestrates the domain; owns no business rules.

↓ depends on

Domain core · pure

Aggregates, entities, value objects, domain events, invariants, the status state machine, repository interfaces. Zero framework references.

The rules that keep it honest

  • Dependency rule: arrows point inward. Domain references nothing; Api references everything, wired only at the composition root.
  • Repositories are interfaces in Domain, implemented in Infrastructure. None returns IQueryable.
  • SaveChangesAsync is the unit of work. No IUnitOfWork wrapper that only forwards.
  • Owned children (status history, medications) are written only through their aggregate root — there is deliberately no repository for them.
  • Shared kernel (BuildingBlocks.Domain / .Application / Contracts) supplies Entity, AggregateRoot, Result<T>, the dispatcher and event contracts — nothing service-specific.

04

Data ownership & the snapshot rule

Every service owns its data outright. There is no shared database and no cross-schema foreign key. Where the read path would otherwise join across services, the fact is snapshotted at write time.

FKs inside, logical refs across

Real database FKs exist only within a schema. A reference like studies.studies.patient_id → identity.patients.id is drawn for readability but never created as a DB constraint — it crosses a service boundary.

Snapshot, don't join

At booking, one typed-HttpClient call copies patient_mrn, patient_name and doctor_name onto the Study. After that the worklist never leaves its own database. This mirrors DICOM itself: PatientName is embedded at acquisition, and a later rename must not rewrite history.

05

Integration events — choreography, not orchestration

Services react to facts. Each event is written to a transactional outbox in the same Postgres transaction as the state change, then relayed by MassTransit — so a fact is never lost and never double-committed. Consumers are idempotent, with a dead-letter queue for poison messages.

EventPublished byConsumed byEffect
ImagesImported Imaging Studies Sets images_imported_at; unlocks the acquisition guard. Status stays todo.
ReportFinalized Reporting Studies Closes the Study: decision=done → done; re_diagnosis → back to a read.
StudyStatusChanged Studies Web (SignalR) Pushes a live status update to the patient portal and doctor worklist.
Why async here: during P04–P07 these hops are temporary direct HTTP calls so each service can be built and tested alone. P08 replaces them with the bus — the boundaries never move, only the transport does. That is the microservice lesson: a service publishes a fact and forgets; whoever cares reacts.
06

The single-writer lock — the differentiator

One doctor edits a Study at a time; everyone else sees it LOCKED. Redis is the authority; Postgres is a durable mirror the UI reads and the auditor trusts.

Release paths

manual (doctor finalized/closed) · ttl_expired (idle sweeper) · admin_force (always audited). Delete uses a Lua compare-and-delete so only the token owner can release.

If they disagree, Redis wins

The mirror can lag; the authoritative answer is always the Redis key. SignalR only announces changes — it is never the source of truth for who holds the lock.

08

Deliberately deferred — the boundary doesn't move

Everything below is re-addable later without relocating a single service boundary. The MVP is a teaching cut of the same product, not a different one.

  • Billing sub-domain — cart, wallet, bills, payments (7 tables). E-commerce; teaches checkout, not imaging or DDD.
  • Prescription service — collapsed into the report_medications child collection on the Report aggregate.
  • Notification service — SignalR toasts cover the demo; email/SMS adds infrastructure, not lessons.
  • Role / permission matrix — replaced by one role column + three policies.
  • Azure + IaC, gRPC, Dapper read models, OpenTelemetry, .NET Aspire, Redis SignalR backplane — infrastructure choices the MVP doesn't need to prove its point; docker compose runs the whole thing.
